# Task 08 — 수동 확인 절차

실제 기기의 패스키(생체 인증/보안 키)가 필요해서 자동 테스트로 대체할 수 없는 항목만 정리한다.
자동으로 확인 가능한 항목(비로그인 거부, 교차 계정 격리, challenge 재사용 거부 등)은 `npm test`와
`VERIFICATION.md`를 참고할 것 — 여기서는 중복 설명하지 않는다.

실행 전 준비: `npm run dev` 실행 후 **일반 브라우저 탭**에서 접속 (Live Preview 등 다른 정적 서버가
같은 포트를 물고 있으면 안 됨). PRIVATE ARCHIVE는 메인 화면 폴더 그리드의 열쇠 아이콘 클릭 → 모달의
"패스키로 열기" 버튼.

## 패스키 두 개 확인

1. 패스키 목록에서 두 개가 보이는 화면 캡처
   - **확인됨 (2026-09-23, `capture/3.png`)**: "패스키 관리" 모달에 "최초 등록 기기"(등록 2026.9.22 오후 11:57:53, 마지막 사용 2026.9.23 오전 9:08:55)와 "새 패스키"(등록 2026.9.23 오전 9:23:26, 마지막 사용 2026.9.23 오전 9:33:21) 두 개가 표시됨. 두 항목 모두 "삭제" 버튼이 활성 상태(둘 다 남아 있으므로 마지막 패스키가 아님).
2. 첫 번째 패스키 삭제
   - "삭제" 클릭 → 확인창("OO 패스키를 삭제할까요? 이 작업은 되돌릴 수 없습니다.")이 뜨는지 확인 → 확인 → 목록에서 사라지고 "삭제했습니다." 메시지가 잠시 떴다가 약 2~3초 뒤 사라지는지 확인. [수동 확인 필요]
3. 로그아웃
   - "로그아웃" 클릭 → 잠금 화면으로 전환, "로그아웃했습니다." 메시지가 잠시 떴다가 사라지는지 확인(이전에는 계속 남아 있던 버그, `js/t08-auth.js`의 `setStatus` 자동 소거 타이머로 수정함 — 수정 전 증거: `capture/1.png`, `capture/4.png`). [수동 확인 필요]
4. 남은 패스키로 로그인 성공
   - "패스키로 열기" → 남은 패스키로 인증 → 잠금 해제, 환영 메시지 확인. [수동 확인 필요]
5. 삭제한 패스키로 로그인 시도 또는 더 이상 선택되지 않는 상태 확인
   - 브라우저의 패스키 선택 화면에 삭제한 패스키가 더 이상 후보로 뜨지 않는지 확인(플랫폼 authenticator UI는 브라우저/OS가 그리므로 이 앱 코드가 직접 통제하지 않음 — 브라우저·OS 차원의 확인). [수동 확인 필요]
6. 남은 마지막 패스키 삭제 시도
   - "삭제" 버튼이 비활성화되어 있고 `title="마지막 남은 패스키는 삭제할 수 없습니다."` 툴크가 뜨는지 확인. 강제로 서버에 DELETE 요청을 보내는 경우(예: devtools)에도 409가 오는지는 자동 테스트(`test/t08/http.test.js`)로 이미 확인됨.
7. 삭제 거절 메시지 확인
   - 클라이언트 버튼이 비활성화되어 있어 정상 흐름에서는 뜨지 않지만, 서버가 409를 반환하는 경우 "마지막 패스키는 삭제할 수 없습니다. 새 패스키를 먼저 등록해 주세요." 문구가 뜨는지 확인(`js/t08-auth.js#deletePasskey`). [수동 확인 필요]

## challenge 확인

자동 테스트(`test/t08/challenge.test.js`, `registration-reject.test.js`, `http.test.js`)로 이미
"매번 새로 생성 / 만료 / 1회용 / 재사용 거부"를 확인했다. 브라우저에서 직접 눈으로 재현하고 싶다면:

1. 개발자 도구 Network 탭을 열고 "패스키로 열기"를 두 번 연달아 클릭(각각 취소)해 `POST /api/t08/auth/options` 응답의 `challenge` 값이 매번 다른지 확인. [수동 확인 필요]
2. "새 패스키 추가"도 마찬가지로 두 번 열어 `POST /api/t08/passkeys/register/options` 응답의 `challenge`가 다른지 확인. [수동 확인 필요]
3. 이미 검증에 사용한 응답을 재전송하는 것은 실제 인증장치 서명이 필요해 브라우저에서 재현하기 어렵다 — 이 경로는 `registration-reject.test.js`의 "replaying the same challenge a second time never succeeds"와 이번에 추가한 `http.test.js`의 미등록 credential 재시도 테스트로 자동 검증됨.

## 등록 취소 확인

1. "패스키 관리" 모달을 열고 현재 패스키 개수를 기록.
2. "새 패스키 추가" 클릭.
3. 브라우저/OS가 띄우는 패스키 생성 창에서 **취소** 선택.
4. "패스키 등록을 취소했거나 시간이 초과되었습니다." 안내가 뜨는지 확인(`js/t08-auth.js#friendlyError`, `NotAllowedError` 분기).
5. 패스키 개수가 취소 전과 동일한지 확인(목록 새로고침 후).
[전체 항목 수동 확인 필요 — 실제 인증장치 취소 동작이 필요함]

## 로그아웃 확인

1. 인증 상태에서 `GET /api/t08/private-items` 200 확인 (devtools Network 탭, 또는 로그인 후 카드 목록이 정상 표시되는 것으로 대체 확인 가능).
2. 로그아웃.
3. 기존 세션 쿠키로 같은 API 재요청(devtools에서 쿠키를 지우지 않고 새로고침하거나, 새 탭에서 재접속).
4. 401 확인.

이 흐름은 `test/t08/http.test.js`의 "after logout, the old session cookie is rejected"로 이미
자동 검증되어 있다. 브라우저에서 재현하려면 위 절차대로 진행하고 결과를 캡처해 남길 것. [수동 확인 필요]
